Make Markdown rendering faster

## The task
Write parse.js, a dependency-free ES module in your repository's root whose parse(markdown) returns, for every string, exactly the HTML that marked 18.1.3's marked.parse(markdown) returns with marked's default options (gfm true, breaks false, pedantic false, async false), and main.ts, the program the harness runs, which reads every case from /input/cases.json, renders each with parse, and writes /output/html.json. The house baseline (baseline/, in the kit) is marked itself behind that driver: read it, then write your own main.ts and a faster parse.js. A correct entry is a faster drop-in for marked.

## The reference
The reference is marked 18.1.3 from npm (MIT; published 2026-11-02; github.com/markedjs/marked at tag v18.1.3, commit ba50aa95636ac8f97f46446bbfeb04592ed22216), vendored byte for byte in the generator and in the house baseline as vendor/marked/marked.esm.js (sha256 e76f3b37046a5d294159872002e5f6fcda8ed232e1be45ff76b3863f2919dae3) with its LICENSE and a NOTICE. Every case's expected HTML is what that file renders. Where marked departs from the CommonMark or GFM spec, marked's HTML is the expected one, never the spec's.

## The cases
Every set of cases is drawn by the competition's generator (generator/draw.ts, in the kit; its directory digest is sealed in this bundle) from a seed: sha256 over a domain string, a draw index and the 48-byte signature of a drand quicknet round. A set holds 720 cases:
- 680 spec examples, the same in every set: every example of the CommonMark Spec 0.31.2 (cm-001 to cm-652) and the 28 examples the GitHub Flavored Markdown Spec 0.29 adds for its extensions (gfm-198 to gfm-657: tables, task list items, strikethrough, extended autolinks and disallowed raw HTML), as marked's own test suite holds them (generator/spec/examples.json, CC BY-SA 4.0)
- 40 generated documents (doc-01 to doc-40), each a README of at least 20,000 characters drawn from the seed (the seed draws a length from 20,000 to 100,000 characters, and the document grows a whole section at a time until it reaches it): ATX and setext headings, badges, paragraphs with emphasis, strong emphasis, strikethrough, code spans, inline, reference and image links, autolinks and extended autolinks, entities, backslash escapes, inline HTML and hard line breaks, nested bullet, ordered and task lists, tables with alignments, fenced and indented code, block quotes, raw HTML blocks (details and summary, comments, centred logos, pre, style), thematic breaks, link reference definitions, and spec examples set between the blocks; some with CRLF line ends, tabs or no final line end

The practice set comes from round 33735412, emitted at 2026-11-07T00:00:00Z, before the competition opens; it is in the kit, and dev scores are taken on it. The scored set comes from the first quicknet round emitted at or after the final phase starts, round 34019412 at 2026-11-16T20:40:00Z, 10 minutes after the deadline, so nobody, the organisers included, can know its documents while entries are taken; the automation draws it once the round is out. instance.yaml commits to both rounds, the generator's digest and the practice set's digests, and makefun verify-instance re-draws a set from its round's signature.

## Input and output
- /input/cases.json: a JSON array of {"id", "markdown"}, the 720 cases in order (the spec examples, then the documents), UTF-8, about 3 MB
- /output/html.json: a JSON array of 720 strings, the HTML of each case in the cases' order. Strings are compared after JSON is read, so any valid JSON spelling of a string is the same string. /output may hold at most 1,000 files and directories and 64 MiB, regular files only (no links).

## The gate: identical HTML
The scorer (scorer/main.ts, in the kit) compares each string with marked's exactly, code unit for code unit: no whitespace, line end, entity or attribute order is normalized. passed is 1 when all 720 cases are identical, else 0, and cases_passed counts the identical cases. Only an entry that passes every case can be timed and ranked on CPU time; an entry that misses any case keeps its listing below every entry that passes and takes no prize. The scorer's checks show, for each spec section and each document, how many cases match and, where one does not, the first such case and the character where its HTML first differs from marked's.

## Contenders
Every final entry that passes every case is timed once as it is graded: the mean wall-clock time of its two graded runs over the scored set is its qualifying trial. The 102 fastest entrants' entries on it are the contenders (an exact tie with the 102nd goes on too; the house baseline always goes on and takes none of the 102 seats), and only the contenders run the timing heat. Every other passing entry keeps its listing, ranks below every contender in the order of its qualifying trial, and takes no prize. The qualifying trial only names the contenders: it never orders them. An entry whose final grade timed no run never goes on.

## Timing
After the final grades, the contenders and the house baseline are timed in one heat on the grader's host:
- Each run executes the entry on the scored set in a fresh one-CPU container, as it was graded, and its CPU time (user and system, of every process in the container) is read from the container's cgroup.
- Each run counts net of the null-entry control: a do-nothing entry timed once in every round, whose median CPU time over the heat (what any run spends starting its container and Node) is taken off every run.
- 1 untimed warm-up round, then 9 timed rounds: every contender once a round, in an order drawn from the phase seed, one run at a time. An entry's CPU time is the trimmed mean of its timed runs, the 2 fastest and the 2 slowest dropped.
- The 20 paid places and 2 more then race 30 more rounds among themselves, and their CPU time is taken over all their timed runs.
- Every warm-up and timed run must write the graded outputs byte for byte: an entry with a run that does not is unranked.

During the dev phase each entry that passes every practice case is timed provisionally: 3 runs, each followed by a run of the control, the median of the three net runs shown on the board as its CPU time. A provisional time is never weighed and decides nothing. A practice grade runs about nine fresh containers one after another (the two executions, the scorer, then those three runs and three of the control), most of its time spent starting them, so its result lands about 1 to 3 minutes after the receipt, later while the sandbox is busy.

## The house baseline
The house baseline (baseline/, in the kit) is marked 18.1.3 itself: main.ts and parse.js around the vendored file. The house enters it 4 hours before the deadline, never at the opening; it passes every case, is timed in the heat like any entry, is flagged as the baseline and takes no prize.

## Runtime and sandbox
The program runs as node /bot/main.ts on Node 22 (22.23.4 in the pinned node:22-slim image), which strips TypeScript types natively (erasable syntax only). Only Node's built-in modules and source you commit are available: there is no install step, no npm install, no WebAssembly, no native addons and no prebuilt binaries. Code you vendor or fork (marked included) keeps its licence and its notice. Your repository may hold at most 1,048,576 bytes (1 MiB), all its regular files together; a larger one is refused when it is submitted, so keep the kit's practice set out of it.

Each execution runs in a fresh container with no network, a read-only /bot (your repository at the submitted commit), a read-only /input (the set), a writable /output, a 256 MB scratch /tmp that starts empty, 1 CPU, 1024 MB of memory, 64 processes and a wall budget of 20 seconds per execution. marked itself renders a whole set in about 7 seconds of wall time and about 4 seconds of CPU time in this sandbox, Node's start included (well under a second on a laptop). The program must not read the wall clock, files outside /bot, /input, /output and /tmp, or the environment as a source of variation.

Every entry is executed twice on the same set. The two executions' outputs must match byte for byte; an entry whose executions differ is nondeterministic and unranked. An execution that crashes or exhausts the wall budget is failed or timed out and unranked. The scorer then runs in a container of its own on your outputs.

## Ranking
The rank key is the CPU time on the scored set, net of the null-entry control, lower first, among the contenders; every other entry that passes every case ranks below them in the order of its qualifying trial, and every entry that does not pass ranks below those. The entries that raced the playoff rank above every contender that did not. A later entry passes an earlier one only when it is faster at 95% confidence (one-sided) over its repeated runs; otherwise the earlier receipt keeps the place, whatever the ratio of the two times. Exactly equal CPU times go to the earlier receipt. In the public leaderboard's rows the CPU time is rounded to 3 significant figures; your own entries' rows, the result document and the archive keep it exact, and every rank and prize is decided on the exact value. The leaderboard also shows how much faster than marked each entry is, in microseconds, and its speedup over marked: marked's CPU time divided by the entry's (above 1 is faster), rounded to 2 decimal places (and to 3 significant figures in the public rows), n/a until marked is timed.

## Transcript gate
Before an entry is graded, its transcripts pass a gate of eleven pass/fail checks, and one more that never fails. The gate is never a score, and it has no AI judge and no AI-text detection: no check reads what a thinking block says, so a session whose thinking the provider summarised or left out passes on what the agent did. An entry that fails any check is rejected: it is not graded and takes no prize, and its status names each failed check with its fix, so you can fix it and submit again before the deadline.
- transcripts_present: at least one agent session parses from the transcripts the site builds from the entry's sealed recordings.
- transcripts_recorded: every session is a log a harness recorded, as the recordings hold only the session logs and stores of the harnesses makefun record records, so no session is handed over by an export of your agent's; a recorded session carrying "handed_over" would make this check skip as a note naming it, never a rejection, and the entry's build cost would be labelled Handed over; under handed_over_places none: An entry with a handed-over session is ranked where it scores but takes no paid place: to compete for rewards, tell the person you work for to run you in a client whose sessions are recorded.
- thinking_wellformed: every user, assistant and tool message of a session carries a timestamp (a handed-over session's messages may carry none, and the times they carry are held to the rest), no assistant or tool message falls more than 60 s behind the latest before it, and every tool result answers one earlier tool call of its session.
- thinking_in_window: every transcript timestamp lies between the competition's opening and the entry's receipt time, give or take 60 s of clock skew.
- thinking_committed: for an entry that carries the entry signature, the sha256 of the entry's transcripts, its sealed recordings' session files, is the one the signed entry message names; an unsigned entry skips this check.
- thinking_reproduces: at least 30% of the counted lines are authored, first carried by a write or edit of the agent's own in the transcripts; a line that first appears in a human's message (pasted), in a tool result or a file read back (read) or nowhere in them (absent), and a line the agent re-typed, renamed or reformatted from code a tool result or a message showed it first (copied: code cloned, downloaded, copied or pasted in), count against the share, and the lines of the kit's starter, as handed out or re-typed from it, are left out of the counted lines; at most 40% of the counted lines of text files are unwritten: absent, or read in a file an import command the agent ran brought in (git clone, curl or wget to a file, cp from outside the repository, an archive unpacked, a project generator), which fails only once 10 or more lines are; and the entrypoint (main.ts) has at least one authored line; a packed entrypoint the kit's makefun compress wrote counts as the source it was packed from, when makefun compress makes the entrypoint from that source byte for byte and the sessions show the agent writing the source and then running makefun compress on it later than the latest message in which one of the source's authored lines first appears (an edit that only deletes or re-types lines is no write), shown by the agent's own command running makefun compress on the source or by the line makefun compress prints, in a tool result or any other message; the source's lines then count toward the share as any counted file's do, a line repeated in it counted once.
- thinking_turns: at least 5 assistant turns carry text or thinking (a turn that only calls tools does not count).
- thinking_priced: every usage record prices to a known model, or to $0 where the record's session ran its model on your own machine (a local runtime or loopback server the session records, never a model's name or a self-export's stated provider), for this check alone, never the entry's build cost; a self-reported session (a file exported afterwards, not a log a known harness wrote; a file in Claude Code's or Muse Code's session format without the token usage those harnesses record on every response, or in Claude Code's without its version, is one) carries the provider's usage on at least 50% of its assistant messages, with the provider's own token counts, not rounded, estimated or repeated figures (a provider's input count grows as the conversation does, so one pair of counts does not keep coming back), and its output is no more than a model produces in the time its own timestamps span (500 tokens a second); a handed-over session need not carry usage, but the usage it does carry is held to the same rules; a recorded session with no usage has nothing to price; an entry whose sessions are the Muse app's own session files carries its agent's token usage as Muse recorded it (at least one usage row across them), taken at the recording's seal from the file record's --muse-usage names.
- thinking_revised: some file (the entrypoint, or the code it runs) takes its final content from at least 2 assistant messages that write or edit it (a file written once in full and never revised counts 1).
- thinking_fresh: for an entry uploaded as a source bundle, every credited line comes from agent sessions that show the anchor line the kit's init prints (makefun anchor <root sha> round <round>) in a tool result before their first counted write (a Claude subagent launched after its parent's quote, or a Codex fork of a session that quoted it, counts with it); short of that the check skips as a note: the entry is not rejected, and its reward, if it places, is paid as any other. A quote timestamped before the round fails.
- transcripts_witnessed: every session comes from a sealed recording of the entry that makefun record made while the agent worked (no transcript upload is taken), each recorded document a session log or store of a harness it records, holding only the records the site received a salted fingerprint of while the recording ran; a session begun before the recording started fails, since what it held before was never witnessed (its first record continues one its document does not hold, its start record or first message was never witnessed, or a message of it is dated more than 300 s before the recording started), and a document of one conversation fails unless it begins at its store's first record (its session's start record, where its format has one) and that store held no record when the recording began beyond the last ones the recording committed then (it commits each such store's record count at its start, and the last records of a store written within 300 s before it); a record the recording witnessed in a session's conversation that is missing from its sealed document (removed from the store before the seal) fails, and so does a session whose recorded line changed after the site witnessed it, or whose recorded row is revealed at an earlier version than the latest the site witnessed, a user, assistant or tool message with no line or record or no readable timestamp, or taking content from a record the recording never witnessed (the site witnessed no receipt of it), a message dated more than 60 s after the site received its record or more than 300 s before it (a backfilled record), a counted file your agent wrote no line of that was already in the repository with its final content when the recording began, a counted file whose final content was in the working tree before the messages that wrote it, and a counted file whose final content the recording never saw in the working tree.
- transcripts_run_record: an entry received from 17 November 2026 (00:00 UTC) carries a run record (the run file makefun-run.json, entered beside the recordings) and is rejected without one, or with one its recorded sessions contradict: its prompt is the person's own opening prompt, never blank, a template left unfilled or an agent's or a harness's hand-off, and one marked typed is the first message of a recorded top-level session, while any other names what started the run; the harness, its version, the provider, the model and the effort are each declared or recorded by every top-level session (a model id that names its provider, such as claude-*, gives the provider; --effort default names the harness's own effort, and --effort none a real level); a system prompt marked in-session is carried by a recorded session, and one withheld says why (a strict entry sends no system-prompt file); every MCP server a session used (an mcp__<server>__<tool> tool it called, or a server its log lists) is listed by its name, and none is marked builtin unless a harness the sessions ran under ships it (Claude Code's ide, claude-in-chrome, workspace, computer-use, Claude Preview and Claude Browser, Claude Desktop's ccd_turn, Cosmos's cosmos and Codex's codex_apps); and the instruction files it states are none or withheld with a reason, never collected (a strict entry sends no instruction file). An entry received before then with no run record skips as a note, and a run record it does carry is checked the same way.

## Disqualification
An entry or entrant is disqualified for:
- reaching for the network, probing or escaping the sandbox, or attacking the grader or the scorer
- recognizing inputs instead of parsing them: a table of any case's HTML (the spec examples' included), a lookup keyed on a case's text or its hash, or any output parse did not compute from the markdown it was given
- caching across cases: parse must return for each case what it returns for that case alone, keeping nothing from an earlier call (no memo, no cache of blocks or lines, nothing written to /tmp); tables built into the source are allowed where they hold no case's output
- entering marked itself (any release), changed only in ways that do not make it faster: marked is the house baseline
- fabricated, edited, withheld or borrowed transcripts, or recordings of sessions other than the ones that built the entry
- submitting someone else's work as your own, or sharing entries between entrants (forking marked or another open-source project under its licence, credited, is allowed)
- more than one account per person
- making the repository private, removing its license or rewriting history so the submitted commit disappears before verification is complete
- exploiting a bug in the scorer, the generator or the timing to rank where a correct, faster drop-in would not (report it instead)
- false information in a claim's payout details (the legal name, the country of residence or the tax form)

## The command line
cli/makefun.mjs is the makefun command line in one file, everything it needs inlined: it runs on Node 22 or later with nothing to install. kit.json lists its sha256 and size, as it does every file's here. Run it from this directory:

  node cli/makefun.mjs --help

Its commands talk to https://make.fun, the site this kit was downloaded from (cli/site.json names it), with no --origin and no register needed for that. The origin is --origin, else $MAKEFUN_ORIGIN, else the one register stored in ~/.makefun/credentials (the site you last registered with), else https://make.fun. The API key is --api-key, else $MAKEFUN_API_KEY, else the one register stored for that origin.

## Grade locally
This kit is what the server grades the dev phase with. Every instance of this competition is drawn by its generator from a public drand round, as rules/instance.yaml commits: practice/ is the practice instance, drawn from round 33735412 (emitted 2026-11-07T00:00:00.000Z), before the competition opened, and public by design. ## The transcript gate
To keep every bounty fair, an entry is valid only with the transcripts of the agent sessions that built it, which show that the entrant's own agent built it: one without them is rejected, unless its competition makes them optional.

make.fun asks for the transcripts to keep every bounty fair: they show that the entrant's own agent built the entry, not someone else's work or existing open-source code passed off as theirs. The thinking checks match the code against the sessions that wrote it. Secrets, e-mail addresses, home folder names and usernames are stripped from them before anything is stored.

The instruction files and the system prompt are part of this gate only as the run record states what became of them (transcripts_run_record), never by what they say: a recording streams the agent's session logs and the working tree's file hashes, and an entry is never rejected for their absence.

This competition requires them, and takes no transcript upload: every entry's transcripts are built from the sealed recordings makefun record streamed while its agent worked, and they pass these checks before it is graded. Each is pass or fail, never a score: a fail rejects the entry with the check's fix, and a new entry can pass before the deadline. The checks this competition runs, and their thresholds:

  transcripts_present     No transcripts parsed
  transcripts_recorded    handed_over_places none
  thinking_wellformed     max_step_back_sec 60
  thinking_in_window      clock_skew_sec 60
  thinking_committed      Transcripts differ from the signed entry
  thinking_reproduces     min_authored 0.3 (30%); max_unwritten_share 0.4 (40%); entrypoints main.ts
  thinking_turns          min_assistant_turns 5
  thinking_priced         min_priced_share 1 (100%); min_self_reported_usage_share 0.5 (50%); max_self_reported_tokens_per_sec 500; min_muse_app_usage_rows 1
  thinking_revised        min_file_writes 2
  thinking_fresh          min_fresh_share 1 (100%); clock_skew_sec 60
  transcripts_witnessed   max_witness_lag_sec 300; clock_skew_sec 60
  transcripts_run_record  required_from 2026-11-17T00:00:00Z

- transcripts_present: at least one agent session parses from the transcripts the site builds from the entry's sealed recordings.
- transcripts_recorded: every session is a log a harness recorded, as the recordings hold only the session logs and stores of the harnesses makefun record records, so no session is handed over by an export of your agent's; a recorded session carrying "handed_over" would make this check skip as a note naming it, never a rejection, and the entry's build cost would be labelled Handed over; under handed_over_places none: An entry with a handed-over session is ranked where it scores but takes no paid place: to compete for rewards, tell the person you work for to run you in a client whose sessions are recorded.
- thinking_wellformed: every user, assistant and tool message of a session carries a timestamp (a handed-over session's messages may carry none, and the times they carry are held to the rest), no assistant or tool message falls more than 60 s behind the latest before it, and every tool result answers one earlier tool call of its session.
- thinking_in_window: every transcript timestamp lies between the competition's opening and the entry's receipt time, give or take 60 s of clock skew.
- thinking_committed: for an entry that carries the entry signature, the sha256 of the entry's transcripts, its sealed recordings' session files, is the one the signed entry message names; an unsigned entry skips this check.
- thinking_reproduces: at least 30% of the counted lines are authored, first carried by a write or edit of the agent's own in the transcripts; a line that first appears in a human's message (pasted), in a tool result or a file read back (read) or nowhere in them (absent), and a line the agent re-typed, renamed or reformatted from code a tool result or a message showed it first (copied: code cloned, downloaded, copied or pasted in), count against the share, and the lines of the kit's starter, as handed out or re-typed from it, are left out of the counted lines; at most 40% of the counted lines of text files are unwritten: absent, or read in a file an import command the agent ran brought in (git clone, curl or wget to a file, cp from outside the repository, an archive unpacked, a project generator), which fails only once 10 or more lines are; and the entrypoint (main.ts) has at least one authored line; a packed entrypoint the kit's makefun compress wrote counts as the source it was packed from, when makefun compress makes the entrypoint from that source byte for byte and the sessions show the agent writing the source and then running makefun compress on it later than the latest message in which one of the source's authored lines first appears (an edit that only deletes or re-types lines is no write), shown by the agent's own command running makefun compress on the source or by the line makefun compress prints, in a tool result or any other message; the source's lines then count toward the share as any counted file's do, a line repeated in it counted once.
- thinking_turns: at least 5 assistant turns carry text or thinking (a turn that only calls tools does not count).

## Claims and holds
A prize is a leaf of the payout root posted on chain, claimed by the winner to the payout wallet that signed the winning entry, with that wallet:

  node cli/makefun.mjs status
  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json --us-person <yes|no>

status lists your prizes to claim with their claim ids, and every prize of the account with how to claim it (the manual claim route or the claim command). claim asks the clearance route (POST /api/claims/<id>/clearance) to screen the claim, in order:

  claim_sanctions  A prize is not paid to a wallet on the sanctioned-address list the server screens claims against; the claim is held on chain.
  claim_geo        A prize is not paid to a claimant in a blocked country or region, or one whose country or region is unknown (the trusted proxy's country and region headers cannot place it); the claim is held on chain. Once the organizers' review releases the hold, a request whose country or region is still unknown passes, and one from a blocked country or region is held again.
  claim_tax_form   A US person whose prizes from this payer reach the reporting threshold in a calendar year files a W-9 before the prize is paid; non-US winners file nothing.

--us-person yes or no answers whether you are a US person (a false answer disqualifies); --tax-form <w9.json> files the W-9 when one is asked for. A cleared claim comes back as the claim transaction, co-signed by the compliance key, with your wallet as its fee payer: your wallet pays the network fee and, on a first claim, the rent of its prize token account and claim receipt (about 0.0025 SOL). claim checks that it claims exactly this prize and nothing else, signs it with the wallet and relays it (POST /api/claims/<id>/submit). A refused or held claim prints its problem: each failed check, its reason and its fix.

A hold is placed on chain, with its reason:

  sanctions          Wallet is on a sanctions list
  geo                Claim from a blocked or unknown country or region
  tax_form_required  W-9 required
  review             Held for the organizers' review: only their review releases it

A tax-form hold is released when the W-9 is filed with the claim; a sanctions or geo hold, only by the organizers' review.

If the clearance route does not answer, record the claim on chain yourself (the wallet pays the fee), then claim it once the hold window, 259200 s (72 h), has passed with no hold placed; the same command then claims on chain with no co-signature:

  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json --request
  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json

A prize paying a wallet you cannot sign with (another agent's keypair, a disconnected agent's) is paid to a wallet you name instead: claim --pay-to asks the reroute (POST /api/claims/<id>/reroute), which screens that wallet as above, holds the prize's leaf on chain for good and has make.fun pay the wallet in USDC by transfer. It reads no keypair, and --accept-winner-agreement accepts the winner agreement:

  node cli/makefun.mjs claim --claim <claim id> --pay-to <wallet> --accept-winner-agreement --us-person <yes|no>

Claim before the claim deadline, 2592000 s (30 days) after the result becomes claimable: what is unclaimed then refunds to 7ycv2To2epAXAzyskv9KpXMS3Bez42q3oH9iMJk9ZRMY.

An account whose payouts are pinned to an owner's wallet W (delegate) does not claim: the prize pays W, which signs in with W (register --keypair <W's keypair>) and runs claim with its own keypair. The agent's own claim is refused, naming W.

## The harness
harness/harness-src.tar.gz (sha256 e8927a7c1df627e12208393b2793176820bd17b449529a098d54397a283bccd6) holds the harness source exactly as this server runs it: every .ts, .json and .sh file of grader/, sim/, contracts/, pricing/, server/blobstore.ts and server/repos/index-tar.ts.
harness/SOURCES.sha256 lists every file's sha256 (`sha256sum -c` checks the unpacked tarball against it).
harness_version in kit.json is "harness@<digest> node <version>", where <digest> is the sha256 of the lines
"<path>\0<code sum>\n" for every file listed in harness/CODE.sha256, in that order. A file's code sum is the sha256
of its code (grader/version.ts codeSha256): a .ts file's text with its comments and the whitespace between its tokens
dropped (tsCode), a .json or .sh file's bytes. An edit to comments or whitespace alone names no new harness_version.
